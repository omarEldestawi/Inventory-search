# Archived Feature: Optical Character Recognition (`RapidOCR` + `RapidTable`)

> **STATUS: FAILED / ARCHIVED (2026-10-25)**
> **DO NOT RE-ENABLE IN PRODUCTION**

## 1. Summary of Failure
The on-demand Optical Character Recognition (`RapidOCR` + `RapidTable` / `🔄 إعادة قراءة بـ OCR / Re-read with OCR`) feature was introduced in Milestone 1 as a fallback for PDF wholesaler catalogs whose layouts were not captured by PyMuPDF's default `page.find_tables()` detector.

In real-world use on Egyptian Arabic pharmaceutical wholesaler catalogs (such as **Zahra Pharm / `تحديث زهره.pdf`**), the OCR feature **never worked** and consistently failed to extract Arabic medication rows:

1. **No Arabic Character Recognition in Bundled ONNX Models**:
   - `rapidocr_onnxruntime` bundles PaddleOCR's Chinese/English recognition model (`ch_PP-OCRv4_rec_infer.onnx`), which has **no Arabic character dictionary or RTL ligature shaping support**.
   - When pages were rasterized at 150 DPI and passed through `RapidOCR`, Arabic item names (`إسم الصنف`) were misread as random Latin/Chinese characters, failing validation (`is_catalog_noise` / Arabic token checks) and yielding **0 items**.
2. **Silent Fallback Masked the Underlying Layout Bug**:
   - Because `parse_ocr()` yielded 0 items from `RapidOCR`/`RapidTable`, its "Tier 3 non-degradation fallback" silently returned the output of the digital parser (`self.parse()`), which on `تحديث زهره.pdf` was the same broken **5 items** out of **1,167 items**.
3. **Unnecessary Bloat**:
   - Bundling `rapidocr_onnxruntime`, `rapid_table`, and `onnxruntime` added over 100 MB of unused ONNX weights and native binaries to the PyInstaller distribution without solving any Arabic catalog layout.

## 2. Root Cause of `تحديث زهره.pdf` Only Showing 5 Items (And Architectural Solution)
All Egyptian pharmaceutical wholesaler PDFs in our corpus—including `تحديث زهره.pdf` (`زهرة فارم لتجارة وتوزيع الأدوية`)—are **100% digital vector PDFs** generated by accounting ERP systems (`ArwaSoft`, `OrgaSoft`, etc.), **not** scanned images.

Specifically, `تحديث زهره.pdf` failed in the digital parser because:
- It uses a **3-column ArwaSoft layout** (Left `x0 ≈ 31.2..212.9`, Middle `x0 ≈ 216.2..398.0`, Right `x0 ≈ 401.4..583.1`).
- Each medication row is enclosed in a drawn vector rectangle (`width ≈ 181.6 pt`, `height ≈ 14.2 pt` in `page.get_drawings()`), **without internal vertical cell dividers** between Discount (`الخصم`), Price (`السعر`), and Item Name (`إسم الصنف`).
- Because there are no vertical grid lines inside the row boxes, `page.find_tables()` returned `0` tables on all 9 pages.
- The parser then fell back to `_extract_dar_fouad_columns()`, which assumed a **2-column** page (`X ∈ [300, 410]` for right-column numbers)—slicing right through the middle of Column 2's medication names and fabricating 5 bogus rows where dosage numbers happened to sit at `X ∈ [300, 410]`.

### The Working Replacement (`_extract_arwasoft_3col_rects` in `src/pdf_parser.py`)
Instead of OCR, `PDFCatalogParser` now inspects vector drawing rectangles (`page.get_drawings()`) and text block coordinates directly via PyMuPDF:
- Detects 3-column ArwaSoft row rectangles (`150 <= width <= 200`, `10 <= height <= 30`) across all 3 columns.
- Slices each rectangle into its exact local horizontal offsets (`Discount: [x0, x0+32)`, `Price: [x0+32, x0+67)`, `Item Name: [x0+67, x1]`).
- Reconstructs multi-line wrapped names, reverses ArwaSoft's inverted Eastern Arabic dosage numerals (`fix_arwasoft_arabic_numbers`), and applies Price/Discount sanity checks.
- Extracts **all 1,167 medication rows (1,166 unique items)** from `تحديث زهره.pdf` in `< 0.25 seconds` with 100% digital accuracy.
